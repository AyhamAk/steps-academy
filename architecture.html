5 — Assumptions and things the code does not state

  1. Railway deployment is inferred, not declared. There is no Dockerfile, docker-compose.yml, Terraform, CDK, railway.json or .github/workflows anywhere in the repo. The deployment target is known only from the CLI being linked to project adventurous-strength and from the API answering on that host. Root directory, pre-deploy command and health check live in Railway's dashboard, so they cannot be verified from the repo.
  2. Supabase is inferred from the connection string host (aws-0-eu-central-1.pooler.supabase.com) in .env.example and the local env. Prisma's provider is simply postgresql; nothing names the vendor.
  3. Games and Shop are drawn as stubs deliberately. Both screens exist and both route groups are mounted, but the controllers return 501 and no client code calls them. A generic template would show a shop as a payments integration — there is no payment provider in this codebase at all.
  4. No cache, queue, or worker exists. No Redis, no BullMQ, no cron service. The only recurring job is setInterval inside the API process (courseCleanup.ts) — it dies with the process and would run once per instance if the service were ever scaled beyond one.
  5. No CDN, load balancer or reverse proxy of our own. Railway's edge terminates TLS; trust proxy 1 exists so rate limiting keys on the real client IP. R2 is private, so images are not CDN-cached — every view is a freshly signed URL.
  6. No error tracking or analytics. No Sentry, no Firebase, no telemetry SDK. Observability is morgan logs in the Railway console.
  7. Google sign-in is drawn as working, but has never run in a real build. It has only been exercised in Expo Go. A release build is signed with a different keystore, and the OAuth client must carry that SHA-1 or sign-in fails.
  8. The local dev environment writes to the production database. steps-server/.env has NODE_ENV=development but points DATABASE_URL at the same Supabase instance Railway serves. This is drawn as a dashed edge in diagram 2 because it is real behaviour, not intent — the seed accounts and placeholder photos in production arrived this way.
  9. The API address is compiled into the app. EXPO_PUBLIC_* values are inlined by EAS at build time, and there is no expo-updates, so a JS-only change still needs a full rebuild and manual reinstall. This is why the custom domain matters: a change of host would otherwise strand every installed app.
  10. README.md and PROJECT_CONTEXT.md are stale — they describe an in-memory backend, Expo Go delivery and an unbuilt "kid mode". Every diagram here follows the code, not those documents.
  11. Photo rows store object keys, never URLs. The one exception is seeded rows carrying an externalUrl to picsum.photos, which is why production still shows placeholder images: no real photo has ever been uploaded through the R2 path in production.
