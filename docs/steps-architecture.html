Section 01

Three actors, one safe triangle

Everything in Steps revolves around the relationship between a child, their parents, and the academy admin. The child never logs in — they are a protected record. The admin controls who is connected to whom, and every photo, notification and course decision flows along those connections and nowhere else.

🧒

Child (Student)

DATA RECORD — NO LOGIN
  • Created only by the admin, never by a parent
  • Owns photo tags, event attendance & course enrollments
  • Can have up to two linked guardians (mum + dad)
  • Identified by ID — two children named “Sara” never collide
👩‍👧

Parent

SCOPED ACCOUNT
  • Sees only photos where their child is tagged
  • Requests course places for their own children only
  • Receives push + in-app notifications about their child
  • Home feed: schedule, next event, courses, announcements
🏫

Admin (Academy)

FULL MANAGEMENT
  • Creates children & links parents — the source of all access
  • Creates events, uploads & tags photos, writes captions
  • Approves / declines course requests (full audit trail)
  • Posts announcements → notifies every family

Section 05

The three core journeys

Every feature in the app is one of these three stories. Each step is labeled with who performs it — parent, admin, or the system acting automatically.

🚪 Journey 1 — From new account to seeing your child

Creating an account is deliberately empty of power. Access is granted by the academy, never claimed by the parent.

  1. 1ParentCreates an account — name, email, password onlyNo child names asked. The form explains: “The academy will link your children to this account.”
  2. 2SystemIssues a JWT session (30 days)bcrypt-hashed password · rate-limited endpoint · session persisted on device, so the app opens straight to Home next time.
  3. 3AdminOpens Management → Students, links the parent to their childSearches the parent by name/email, taps “Link”. Both mum and dad can be linked to the same child.
  4. 4SystemThe ParentStudent link now exists — everything unlocksChild chip appears on Home & Profile, the gallery fills with their child's photos, notifications begin flowing.
  5. 5ParentSees exactly one thing: their own child's worldPhotos, courses and notifications are all filtered through the link — nothing else is reachable.
🔒 Why it works this way: if parents could type their child's name, any parent typing “Sara” would see every Sara's photos. Access must be granted by the academy, by ID.

📸 Journey 2 — The photo pipeline

From the admin's camera roll to a parent's push notification, without a single public URL.

  1. 1AdminCreates an event and picks which children attendedAttendees are chosen from enrolled students — chips, not typing. An optional caption (“What an amazing day! 💦”) is shown to parents.
  2. 2AdminUploads photos to the eventMulti-select from the photo library with per-file progress bars.
  3. 3Systemsharp resizes every photo into 3 sizes → Cloudflare R2thumbnail ~200px · medium ~800px · original. The bucket is fully private.
  4. 4SystemAuto-tags every attendee in every photoPhotoTag rows by student ID. The admin can fine-tune tags per photo afterwards.
  5. 5SystemNotifies each child's guardians — once per child, not per photoIn-app notification + push: “New photos of Layla — 12 new photos from Art Show”.
  6. 6ParentOpens the gallery, sees only photos their child is tagged inEvery image loads through a 1-hour signed URL. Fullscreen viewer with save & share.
✅ Privacy guarantee: two families each with a child named “Sara” were tested head-to-head — each parent sees only their own child's photo. Matching is by ID, never by name.

🎓 Journey 3 — Course enrollment with approval

A request → review → decision workflow. Nothing is first-come-first-served; the academy stays in control, and everything is logged.

  1. 1ParentTaps “Request a place” on a course cardIf they have several children, they pick which child. The server verifies guardianship — you can only request for your own child.
  2. 2SystemCreates a pending enrollment — card flips to “⏳ Awaiting approval”Recorded: who asked and when. A pending request can be withdrawn by the parent.
  3. 3AdminReviews the board — requests grouped by courseSticky course headers with counts, filters (pending / approved / declined / all), pending badge on the dashboard.
  4. 4AdminApproves or declinesCapacity is enforced at approval — requests may exceed spots, and the admin chooses who gets in. Decision + decider + timestamp + optional note are stored forever.
  5. 5SystemNotifies the child's guardians of the decisionPush + in-app: “Course request approved 🎉 — Layla is enrolled in Swimming Lessons.”
  6. 6ParentCard shows the truth: “✓ Layla is enrolled” / “Request again”A declined family can re-request — it reopens the same record, keeping one continuous history per child + course.
📒 Everything is logged: every enrollment permanently records requested by / at and decided by / at — a complete audit trail the academy can always answer questions from.

Section 08

Security model

This is an app that holds photos of other people's children. The design treats that as the primary constraint, not a feature.

🔑

Access = a database link

THE CORE RULE
  • Photo visibility is a foreign-key match on Student ID
  • Never name matching — same-named children can't collide
  • Only admins create the parent ⇄ child link
  • Registration grants zero access by itself
🗄️

Nothing is public

STORAGE
  • R2 bucket is fully private — no public objects
  • Every image read is a 1-hour signed URL, minted per request
  • The old public /uploads route was removed entirely
  • Photos of children never touch a public CDN path
🛡️

Hardened API

TRANSPORT & AUTH
  • JWT on every request; server re-checks the user still exists
  • Rate limiting on register / login / Google (20 per 15 min)
  • bcrypt password hashing · JWT secret fails fast in prod
  • Client auto-logs-out on 401 — stale sessions can't linger
  • helmet headers · CORS restricted via environment config
Section 09

How it's built & run

A monorepo with two halves. During development the native app is installed once, then every JavaScript change streams to the phone live from Metro.

📂 Repository layout

Steps/
├─ steps-app/          # Expo React Native app
│  ├─ src/app/          # expo-router screens
│  │  ├─ (tabs)/        # Home · Gallery · Profile
│  │  ├─ admin.tsx      # management dashboard
│  │  ├─ students.tsx   # children & guardians
│  │  └─ course-requests.tsx
│  ├─ src/components/   # ui · gallery · home · profile
│  ├─ src/services/     # typed API clients
│  ├─ src/store/        # zustand (auth · locale)
│  └─ src/i18n/         # en · ar · he dictionaries
└─ steps-server/       # Express API
   ├─ prisma/           # schema + migrations
   └─ src/
      ├─ controllers/   # request handlers
      ├─ models/        # Prisma data access
      ├─ routes/        # endpoint definitions
      ├─ middleware/    # auth · roles · rate limit
      └─ lib/           # r2 · push · image pipeline

⚡ The development loop

# 1 · start the API (terminal 1)
cd steps-server
npm run dev              # tsx watch · :4000

# 2 · start the app bundler (terminal 2)
cd steps-app
npx expo start --dev-client

# open the installed Steps app on the phone —
# it pulls the JS bundle live from Metro.
# Every save hot-reloads on the device. ⚡

📦 Native builds (only when native changes)

# development client — for daily work
npx eas-cli build --profile development --platform ios

# preview — standalone, for handing to testers
npx eas-cli build --profile preview --platform ios

# JS-only changes NEVER need a rebuild.
# Rebuild only for: new native modules,
# app.json icon/splash/permissions/plugins.
🌍 Internationalization is not a bolt-on: every string in the app exists in English, Arabic and Hebrew, and every screen mirrors correctly right-to-left. RTL is handled in JavaScript so it works identically across build types.
